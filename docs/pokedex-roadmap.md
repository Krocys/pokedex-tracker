## 2. Требования к продукту

### 2.1 Профили покедексов
- Несколько независимых профилей у одного пользователя («Национальный», «Прохожу Emerald», «Shiny-хант в SV»).
- Профиль привязан к **игре** либо к **национальному дексу**.
- **Тип профиля**:
  - `final` — только финальные формы эволюционных линий (~613 записей);
  - `living` — живой декс, по одному экземпляру каждого вида (~1091);
  - `living-forms` — живой декс со всеми формами отдельно (~1396).
- **Чекбокс «Shiny»** в настройках профиля, рядом с выбором игры. Если включён — во всём профиле спрайты подменяются на shiny-версии. Отдельного shiny-декса нет: это просто ещё один профиль с включённой галочкой.
- Прогресс считается независимо для каждого профиля.

**Валидация при создании:** shiny-профиль невозможен для игр 1 поколения (Red / Blue / Yellow) — блестящие покемоны появились только во 2 поколении. Чекбокс блокируется при выборе такой игры. Мелочь, но на защите выглядит как понимание предметной области.

### 2.2 Состояние покемона: три значения

| Код | Значение | Смысл |
|---|---|---|
| `none` | Не пойман | Состояние по умолчанию |
| `has_prevo` | Есть предэволюция | Нужная форма не получена, но в наличии есть свободный экземпляр **любой** более ранней формы этой линии |
| `caught` | Пойман | Готово |

Ставится **вручную**. Автовывод («если пред-форма отмечена в этом же профиле — считать `has_prevo`») делать нельзя: в дексе типа `final` предэволюций в списке вообще нет, а в `living` они считаются самостоятельными записями, и автомат бы засчитывал одного и того же покемона дважды.

**Важно: не только соседняя ступень.** Пример — есть Bulbasaur и Ivysaur, нужен Venusaur, и в запасе лежит второй Bulbasaur. Venusaur отмечается как `has_prevo`, хотя его непосредственная предэволюция — Ivysaur, а не Bulbasaur. Значит проверка «на одну ступень назад» неверна: смотреть надо на всю линию.

**Порядок переключения по клику:** `none → has_prevo → caught → none`, то есть по нарастанию прогресса. Дополнительно — заметка и дата.

**В статистике** это три отдельных счётчика:
- основной процент — только `caught`;
- «в шаге от завершения» — `has_prevo`;
- «потенциальный процент» — `caught + has_prevo`.

Готовый материал для пункта ТЗ #12 («производятся расчёты и ведётся статистика»).

### 2.2.1 Язык

Интерфейс, сообщения, валидация, документация — **русский**.
Всё, что относится к предметной области — имена покемонов, типы, названия локаций, методы встречи — **английский**, как в играх.

Следствия:
- словарь переводов не нужен, экономим примерно неделю на этапе данных;
- поиск работает по английским именам и по номерам;
- **но ER-диаграмма и описание таблиц по ТЗ должны быть на русском**, а код — на английском. Значит нужен глоссарий соответствия («Пользователь → `users`», «Отметка о поимке → `catches`»), иначе диаграмма и код разойдутся и на защите будет неудобно.

### 2.3 Список покедекса
- Сетка карточек: спрайт, номер в текущем дексе, имя, типы, статус.
- **Поиск** по имени и номеру (с debounce).
- **Фильтры**: тип, поколение, статус (не пойман / есть предэволюция / пойман), форма, эволюционная стадия.
- **Сортировка**: номер в дексе, национальный номер, имя, тип.
- **Пагинация** (по 24–48 карточек).

### 2.4 Карточка покемона
- **Где поймать** — только для игры текущего профиля.
- **Кнопка «Найти на YouTube»** — всегда, независимо от наличия данных о локации.
- **Эволюционная ветка** в контексте профиля: показываем всю линию, помечаем кто входит в текущий декс и кто недоступен в этой игре.

### 2.5 Роли (минимум 3)
| Роль | Может |
|---|---|
| **user** | Регистрация, свои профили, отметки, своя статистика |
| **manager** | Всё что user + CRUD справочника локаций и встреч, подсказки к покемонам, пресеты дексов |
| **admin** | Всё что manager + управление пользователями: роли, блокировка, удаление, общая статистика |

## 3. Ключевые технические решения

### 3.1 Источник данных: PokeAPI + известное ограничение

Схема: **генерация статических JSON на этапе сборки**. Node-скрипт запускается один раз, приложение работает с готовыми файлами.

**Что PokeAPI закрывает полностью (1–9 поколения):**

| Нужно | Эндпоинт |
|---|---|
| Виды, формы, типы, спрайты (обычные и shiny) | `/pokemon/{id}`, `/pokemon-species/{id}` |
| Национальный декс | `/pokedex/national` |
| Дексы конкретных игр | `/pokedex/{id}` (kanto, updated-johto, galar, paldea, kitakami, indigo-disk…) |
| Игры и version-group | `/version-group`, `/version` |
| Эволюционные цепочки и условия | `/evolution-chain/{id}` |
| Локации поимки | `/pokemon/{id}/encounters` — **см. ниже** |

**Критическое ограничение: encounters есть только до 7 поколения.**
Для 8 и 9 поколений (SwSh, BDSP, PLA, SV, PLZA) `/encounters` возвращает пустой массив. Мейнтейнеры это подтверждают, работа по добавлению ведётся, но к декабрю рассчитывать на неё нельзя.

**Стратегия деградации (и это подаётся как проектное решение, а не как баг):**

| Ситуация | Что показываем |
|---|---|
| Есть данные в PokeAPI (1–7 ген) | Список локаций с методом, уровнями, шансом |
| Есть ручные данные от менеджера | Список локаций с пометкой «данные внесены вручную» |
| Данных нет (8–9 ген) | Блок «данные о локациях недоступны» + кнопка YouTube |
| Всегда | Кнопка `youtube.com/results?search_query=` + `имя + game + "location"` |

Это одновременно: снимает риск проекта, даёт менеджеру осмысленную работу и красиво защищается в записке как «архитектура, устойчивая к неполноте внешнего источника».

**Практическая оптимизация выгрузки.** Вместо ~1300 запросов к API можно склонировать репозиторий `PokeAPI/api-data` — там лежат уже сгенерированные JSON всех эндпоинтов. Это быстрее, не нагружает публичный API и не требует обработки rate-limit. Если качаем через API — обязательно кэш на диск и задержка между запросами.

### 3.2 Формы: списки берём из таблицы Austin John

**Статус: проверено на данных, результат ниже.**

Самый трудоёмкий вопрос проекта — «что считать отдельной записью в живом дексе со всеми формами». В загруженной таблице это уже выверено:

| Лист | Записей | Тип профиля |
|---|---|---|
| `FinalForm` | 612 | `final` |
| `Living` | 1090 | `living` |
| `LivingForm` | 1395 | `living-forms` |

**Связывать с PokeAPI надо по паре «имя + Form name», а не по столбцу `Keyword`.**
`Keyword` позиционно-нумерованный: Alolan Meowth — это `meowth-1`, Galarian — `meowth-2`, номер зависит только от порядка добавления формы. В PokeAPI это `meowth-alola` и `meowth-galar`, соответствия между схемами нет. Столбец `Form name` семантический («Alolan», «Galarian», «Hisuian», «Red Flower», «Original Cap»), по нему всё и мапится.

**Замеренное покрытие автоматики** (пустая форма / `Original` / `Normal` + четыре региональных префикса):

| Тип декса | Записей | Мапится авто | Нужны правила | % авто |
|---|---|---|---|---|
| `living` | 1090 | 1087 | 3 | 99.7% |
| `final` | 612 | 610 | 2 | 99.7% |
| `living-forms` | 1395 | 1155 | 240 | 82.8% |

240 непокрытых записей сидят в сорока покемонах и почти все алгоритмические:
Alcremie (63 = 9 кремов × 7 сладостей), Unown (28 = 26 букв + `!` и `?`), Vivillon (20 узоров), Furfrou (9 стрижек), кепки Pikachu (8), Minior (7), линия Flabébé/Floette/Florges (16), Rotom (5), сезонные Deerling и Sawsbuck (8), Gourgeist и Pumpkaboo (8). Пишется десятком паттернов, а не таблицей на 240 строк. Полный список — в `needs-rule.json`.

**Пол — это модификатор спрайта, а не отдельный покемон.**
112 записей с гендерным различием есть только в `living-forms`. Отдельных сущностей для них в PokeAPI в основном нет (исключения — Meowstic, Indeedee, Basculegion), но есть поля `front_female` и `front_shiny_female`. Вместе с профильным флагом shiny выбор спрайта становится матрицей 2×2:

```js
getSprite(pokemon, entry, profile) =>
  profile.isShiny
    ? (entry.isFemale ? front_shiny_female : front_shiny)
    : (entry.isFemale ? front_female       : front_default);
```

Фолбэк обязателен: у части редких форм женского или shiny-спрайта в API нет, тогда откатываемся на `front_default` с пометкой в интерфейсе.

**Готовые артефакты:** `living-forms.json`, `living.json`, `final.json` (поля `nat`, `name`, `formName`, `ajKeyword`, `pokeapiSlug`, `isFemale`, `mapping`), `needs-rule.json`, скрипт `extract-dex-lists.py`. Скрипт одноразовый — результат коммитится в репозиторий, поэтому Python в проекте не остаётся; при желании переписывается на Node с пакетом `xlsx` за полчаса.

### 3.3 Разделение данных на два слоя

**Слой 1 — справочник (read-only, поставляется с приложением):**
покемоны, формы, виды, типы, поколения, игры, дексы, вхождения в дексы, локации, встречи, эволюции.

**Слой 2 — пользовательские данные (пишутся в рантайме):**
роли, пользователи, сессии, профили дексов, отметки о поимке.

### 3.4 «БД в json» (пункт #33)

- Стартовый «дамп БД» — `data/seed/*.json`.
- При первом запуске сеется в `localStorage` — это и есть «реализация БД».
- Тестовые данные: 3 пользователя (по одному на роль), 2–3 профиля с частичным прогрессом.
- Пароли: SHA-256 + соль через `crypto.subtle`. В записке честно оговариваем, что клиентское хеширование — не полноценная защита, и на этапе бэкенда переезжает на сервер.

**Про объём.** 1300+ покемонов × 9 поколений локаций — это десятки мегабайт, в localStorage (лимит ~5 МБ) не влезет. Поэтому:
- справочник — только `fetch` из `data/`, **никогда** не в localStorage;
- справочник разбиваем по файлам: `pokemon.json` (лёгкий, только для списка), `encounters/gen-N.json` и `evolutions.json` грузим лениво при открытии карточки;
- в localStorage — только пользователи, профили и отметки (одна отметка ≈ 40 байт, 1400 отметок × 5 профилей ≈ 300 КБ, влезает с запасом).

### 3.5 Задел под бэкенд

Всё общение с данными — через репозитории с единым интерфейсом:

```
IUserRepository:    getById, getByLogin, create, update, delete, list
IProfileRepository: listByUser, create, update, delete
ICatchRepository:   listByProfile, toggleCaught, toggleShiny
```

Сейчас — `LocalUserRepository` (localStorage). Потом добавляется `HttpUserRepository`, и **ни одна страница не переписывается**: меняется одна строка в фабрике.

**Все методы делаем `async` уже сейчас**, даже поверх синхронного localStorage. Иначе при переезде на сеть придётся переписывать весь UI.

## 4. Модель данных (для ER-диаграммы)

**Справочник**
- `generations` (id, code, name)
- `species` (id, nat_number, name, evolution_chain_id, generation_id)
- `pokemon` (id, species_id, form_code, form_name, is_default, sprite, sprite_shiny)
- `types` (id, code, name_ru)
- `pokemon_types` (pokemon_id, type_id, slot)
- `games` (id, code, title, generation_id, release_year)
- `dexes` (id, game_id — NULL для национального, code, name)
- `dex_entries` (id, dex_id, pokemon_id, dex_number)
- `locations` (id, game_id, name)
- `encounters` (id, pokemon_id, location_id, method, min_level, max_level, chance, source)
- `evolution_links` (id, from_pokemon_id, to_pokemon_id, method, condition)

**Пользовательские данные**
- `roles` (id, code, name)
- `users` (id, login, email, password_hash, salt, role_id, is_blocked, created_at)
- `sessions` (id, user_id, token, created_at) — нужна для запрета повторной авторизации
- `profiles` (id, user_id, name, dex_id, dex_type, **is_shiny**, created_at)
- `catches` (id, profile_id, pokemon_id, **status** ENUM(`has_prevo`, `caught`), caught_at, note)

Два решения по `catches`:
- **shiny ушёл из отметок в профиль** — это свойство всего декса, а не отдельного покемона. Функция выбора спрайта становится тривиальной: `getSprite(pokemon, profile) → profile.is_shiny ? sprite_shiny : sprite`.
- **строки для `none` не храним.** Нет записи — значит не пойман. При 1396 покемонах и пяти профилях это разница между 7000 строк и парой сотен, что для localStorage существенно.

16 сущностей — достаточно для курсовой, нормализация до 3НФ показывается наглядно на связях «покемон — тип» и «встреча — локация».

Поле `encounters.source` (`api` / `manual`) — то, что делает роль менеджера видимой в модели данных.

## 6. Что режем первым, если отстаём

По порядку, от наименее болезненного:
1. Локальное хранение спрайтов → оставляем CDN PokeAPI.
2. Экспорт / импорт профиля в JSON.
3. График на canvas → простые полоски прогресса на CSS.
4. Ручной CRUD локаций у менеджера → урезаем до редактирования подсказок.
5. Сортировка по типу и фильтр по эволюционной стадии.
6. Состояние `has_prevo` → оставляем два состояния. Это последнее, что режем: оно даёт содержательную статистику.

**Не режем никогда:** пункты ТЗ #16, #20, #12 (поиск + фильтрация + статистика + внесение данных), три роли, адаптив. Это то, что проверяется по чек-листу.

## 7. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Локации 8–9 гена отсутствуют | **Подтверждено** | Стратегия деградации из п. 3.1, YouTube-кнопка всегда |
| ~~Формы из xlsx не мапятся на PokeAPI~~ | **Снят** | Замерено: 82.8% авто в худшем случае, остаток покрывается паттернами |
| Нет женского или shiny-спрайта у редкой формы | Средняя | Фолбэк на `front_default` с пометкой в интерфейсе |
| localStorage переполняется | Средняя | Справочник только через fetch, в хранилище только отметки |
| Тормоза на 1300+ карточках | Средняя | Пагинация + lazy-загрузка спрайтов |
| Записка оставлена на конец | **Высокая** | Раздел пишется сразу после закрытия этапа |
| Хочется сделать всё и сразу | **Высокая** | Список сокращений из п. 6, применять без сожалений |
